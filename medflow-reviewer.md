# MedFlow Knowledge Review Checklist

Companion to the MedFlow Ecosystem spec. This is what to actually understand — not just copy — before and during each build phase. If you can't explain an item to someone else, you're not ready to build the phase that needs it.

How to use this: don't try to learn everything before Phase 1. Study the "before you start" section now, then read each phase's list right before you begin that phase, not before.

---

## Before you start anything

**Python fundamentals you can't skip**
- The difference between concurrency and parallelism, and why the GIL makes them different things in Python specifically.
- `async`/`await` — what actually happens at an `await` point, and why calling a blocking function inside an async function stalls the whole event loop.
- Context managers (`with`), since you'll use them constantly for database sessions and transactions.

**Relational database basics**
- ACID, and specifically what "isolation" means in practice — what two transactions can and can't see of each other mid-flight.
- What a transaction actually is: a unit of work that either fully commits or fully rolls back.
- Primary keys, foreign keys, and why cross-service foreign keys are what you're avoiding by keeping each service's database isolated.

**Self-check:** can you explain why two people booking the same appointment slot at the same millisecond is a real problem, without using the word "race condition" as a magic incantation you don't actually understand?

## Phase 1: Foundation — Auth, Docker, one working service

**Stack knowledge**
- Docker Compose: services, volumes, networks, and what `depends_on` does and doesn't guarantee (it does not wait for Postgres to be *ready*, only for the container to *start* — this trips people up constantly).
- FastAPI dependency injection — how `Depends()` works, since your JWT-validation middleware will be one.
- SQLAlchemy 2.0's session lifecycle: when a session opens, when it flushes, when it commits, and what happens if you forget to close one.
- Alembic migrations: what an autogenerated migration actually detects, and why you should always read one before applying it.

**Domain and security knowledge**
- JWT structure: header, payload, signature — and specifically why you're using RSA (asymmetric) instead of a shared secret. Every service can verify a token without being able to forge one. Know why that distinction matters before you build it.
- bcrypt and why you never write your own password hashing.
- RBAC vs. simpler role checks — the difference between "is this user a doctor" and "does this user have the `encounters:write` permission." You're building the second one; know why it scales better.

**Self-check:** if the Auth service's private key leaked, what could an attacker do? If you're not sure, you don't understand the trust model you're building yet.

## Phase 2: Core clinical flow, no event bus yet

**Stack knowledge**
- `SELECT FOR UPDATE`: what row it actually locks, how long the lock is held, and what happens to a second transaction that hits the same row while it's locked (it waits — know how long, and what a deadlock looks like when two transactions lock rows in opposite order).
- JSONB in Postgres: when it's the right call versus a normalized table, and how indexing a JSONB field works (GIN indexes).
- Redis as a cache: cache invalidation strategy — specifically, what invalidates a cached patient profile when the underlying record changes. This is the part people skip and then wonder why stale data shows up.

**Domain knowledge**
- What actually goes in an encounter note, structurally — chief complaint, history, assessment, plan (SOAP format is the common one). You don't need to be clinical, but you need to know why this data is shaped the way it is before you design the schema.

**Self-check:** two nurses try to book the last slot in a doctor's schedule at the same time. Walk through exactly what happens at the database level, statement by statement.

## Phase 3: The event bus, end to end

This phase has the steepest learning curve in the whole project. Don't rush it.

**Stack knowledge**
- The outbox pattern, specifically *why* it exists: what goes wrong if you publish to Redis directly inside a route handler (the "dual write" problem — your database commits, then the process crashes before the Redis publish happens, and now your system's state and your event log disagree forever).
- Redis Streams: consumer groups, message acknowledgment, and what happens to an unacknowledged message if a consumer crashes mid-processing.
- Idempotency: if the same `prescription_created` event gets delivered twice, what stops your system from deducting stock twice? You need an answer to this before you write the consumer, not after you find a bug.

**Domain knowledge**
- FIFO inventory logic in a real pharmacy context: why expiration date, not arrival date, usually drives dispense order, and what a "batch" actually represents (a specific lot from a specific manufacturing run, not just "some units of drug X").

**Self-check:** kill the Redis Stream consumer mid-transaction, on purpose, in your test environment. Does the stock get deducted twice, zero times, or exactly once when it restarts? If you don't know the answer without running it, you don't understand the guarantees you've built yet — go find out.

## Phase 4: Remaining services

**Stack knowledge**
- Webhook handling: signature verification (so you're not processing forged lab results), and idempotency again — labs will occasionally resend the same webhook.
- Background workers vs. request-response: why a denial-risk prediction runs as a worker that picks up events, not as something the billing route handler waits on synchronously.

**Domain knowledge**
- NEWS2 scoring: the six vital-sign parameters it weighs (respiration rate, oxygen saturation, systolic blood pressure, pulse rate, consciousness level, temperature) and roughly how the banding works. You don't need clinical judgment, but you do need to understand why it's a fixed lookup table, not a model — that's *why* it doesn't need heavy compute.
- ICD-10 and CPT codes at a structural level: ICD-10 describes *what's wrong with the patient* (diagnosis), CPT describes *what was done about it* (procedure). Billing needs both, mapped correctly, or claims get denied. That distinction alone will save you a confusing debugging session later.

**Self-check:** explain, in one sentence each, the difference between what LIS and Triage actually compute versus what they just relay.

## Phase 5: Security, compliance, platform

**Domain knowledge — this is the phase where "I'll look it up later" actually costs you**
- HIPAA's core concept isn't a checklist, it's a principle: minimum necessary access. Every permission you grant should map to "does this role need this specific data to do this specific job," not "give doctors everything, it's easier."
- What PHI (protected health information) actually covers — it's broader than people assume. A patient's name next to an appointment time is PHI. So is a correlation ID if it can be linked back to a specific person's records.
- Encryption at rest vs. in transit — you need both, and they solve different threats (a stolen disk vs. an intercepted request).

**Stack knowledge**
- Secrets management: why environment variables in a `.env` file committed to git is the single most common real-world security failure, and what a proper secrets manager actually buys you (rotation, audit trail of who accessed what).
- What "observability" means beyond logging: the difference between logs (what happened), metrics (how much/how often), and traces (the path one request took across services). You need a correlation ID strategy that ties all three together, which you already started in Phase 1 — this is where it pays off.

**Self-check:** if a regulator asked "show me every person who accessed patient X's record in the last 90 days," could your system answer that today? If not, that's the gap this phase closes.

## Phase 6-7: Gateway, BFF, and UI

**Stack knowledge**
- API gateway responsibilities vs. BFF responsibilities — a gateway does generic cross-cutting concerns (rate limiting, auth), a BFF does UI-specific data shaping (aggregating three services into one response a screen needs). Conflating the two turns your gateway into an unmaintainable mess over time.
- React fundamentals if you're not already solid: component state vs. server state (the data your API owns — don't duplicate it awkwardly in local state), and why role-based routing needs to be enforced by the backend permission check, not just by hiding a link in the UI.
- WebSockets vs. Server-Sent Events: SSE is simpler and one-directional (server to client), which is exactly what a triage alert needs — you're not sending data back over that channel, so don't reach for the more complex tool.

**Domain knowledge**
- Basic clinical UI conventions: why critical alerts in healthcare software are typically red and require acknowledgment (a dismissible toast that vanishes in 3 seconds is the wrong pattern for "this patient's vitals just crossed a critical threshold").

**Self-check:** a nurse's session token gets used from a browser tab that's been left open on the doctor's dashboard URL. What actually stops that from working? If the answer only lives in the frontend router, it's not actually enforced.

## Phase 8: Testing and deployment

**Stack knowledge**
- The test pyramid: unit tests (cheap, fast, test one function), integration tests (test a service talking to its real database), contract tests (test that Service A's expectations of Service B's API still hold — critical in a microservices setup, since you can't test everything end to end on every change).
- What a deployment target actually constrains: a single VM, Kubernetes, and a managed platform (like a PaaS) each impose different assumptions about how your services discover each other, handle secrets, and scale — decide this before writing CI/CD, not after.

**Self-check:** if you changed a field name in the Pharmacy dispense event, what would tell you Billing's consumer just broke, before a claim silently failed to generate? If the answer is "nothing, we'd find out in production," that's what contract testing in this phase is for.

---

## A note on pacing

You don't need to master all of this before writing a line of code. Read the "before you start" section now. Read each phase's section right before that phase, work through the self-check honestly, and move on. If a self-check stumps you, that's not a sign to go read a textbook cover to cover — it's a sign to go build a tiny throwaway script that answers exactly that question, then come back to the real service.
