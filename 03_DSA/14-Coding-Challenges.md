Module 14: System Design Fundamentals for Backend EngineersLearning ObjectivesBy the end of this module, you will be able to:Distinguish between vertical and horizontal scaling.Understand the role of Load Balancers, API Gateways, and Caching layers in enterprise architecture.Apply the CAP Theorem to make informed database choices (SQL vs. NoSQL).Structure a System Design interview using a proven framework.Architect a high-level solution for a common distributed system problem (e.g., URL Shortener).IntroductionWhile data structures and algorithms (Module 13) prove that you can write efficient code on a single machine, System Design proves that you can build architectures capable of serving millions of users across multiple servers. For Mid-Level to Senior Enterprise Backend roles, the System Design interview is often the most heavily weighted part of the hiring process. Interviewers want to see how you balance trade-offs, manage state, and prevent single points of failure.Part 1: Core Architectural Concepts1. Scalability: Vertical vs. HorizontalWhen your server is overwhelmed by traffic, you have two ways to scale:Vertical Scaling (Scaling Up): Adding more CPU, RAM, or storage to your existing server.Pros: Simple. No code changes required.Cons: Has a hard hardware limit. A single server is still a single point of failure (SPOF).Horizontal Scaling (Scaling Out): Adding more servers to your resource pool.Pros: Virtually infinite scalability. Adds redundancy/fault tolerance.Cons: Highly complex. Requires load balancers, stateless backend applications, and distributed databases.2. Load BalancingA Load Balancer (like NGINX or AWS ALB) sits in front of your horizontally scaled servers. It acts as a traffic cop, distributing incoming HTTP requests evenly across your servers so no single machine gets overwhelmed.Common Algorithms: Round Robin, Least Connections, IP Hashing (useful for sticky sessions).3. CachingFetching data from a database is an expensive I/O operation. Caching temporarily stores frequently accessed data in memory (RAM) for lightning-fast retrieval ($O(1)$ time complexity).Technologies: Redis, Memcached.Enterprise Use Case: Caching a user's session token or the top 100 most popular products on an e-commerce home page.4. Database Scaling: Replication and ShardingReplication: Copying data from a primary database (Write node) to multiple replica databases (Read nodes). This solves read-heavy traffic bottlenecks.Sharding: Splitting a massive database into smaller, faster pieces across multiple servers based on a shard key (e.g., storing users A-M on Server 1, and N-Z on Server 2).Part 2: The CAP TheoremThe CAP Theorem is a fundamental principle of distributed data stores. It states that a distributed database can only guarantee two out of the following three traits at any given time:Consistency (C): Every read receives the most recent write or an error. All nodes see the exact same data at the exact same time.Availability (A): Every request receives a non-error response, without the guarantee that it contains the most recent write.Partition Tolerance (P): The system continues to operate despite an arbitrary number of messages being dropped or delayed by the network between nodes.The Trade-off: Because network failures (Partitions) are inevitable in the real world, distributed systems must always choose 'P'. Therefore, backend engineers must choose between CP (Consistency + Partition Tolerance) or AP (Availability + Partition Tolerance).Banking System: Needs CP. It is better to decline a transaction (lower availability) than to show incorrect account balances (inconsistency).Social Media Feed: Needs AP. If a user's feed is delayed by 5 seconds (inconsistent), it's fine, as long as the app loads quickly and doesn't crash.Part 3: The System Design Interview Framework (The "PEDALS" Method)Never jump straight into drawing architecture diagrams. Use a framework to structure your 45-minute interview.P - Process the Requirements (5 mins): Clarify the functional requirements (e.g., "Users can upload photos") and non-functional requirements (e.g., "System must be highly available and handle $10,000$ requests per second").E - Estimate the Scale (5 mins): Do back-of-the-envelope math. Calculate storage needs per day, Read-to-Write ratio, and bandwidth.D - Data Model & API Design (10 mins): Define your database schema (SQL vs. NoSQL) and outline your core REST or GraphQL endpoints.A - Architecture High-Level Design (10 mins): Draw the happy path. Show the Client -> Load Balancer -> Web Servers -> Database.L - Look for Bottlenecks (10 mins): Identify single points of failure. Where will the system break under 10x load?S - Scale & Optimize (5 mins): Add caching layers, read replicas, CDNs, or message queues (like Kafka or RabbitMQ) to resolve the bottlenecks.Part 4: Practice Scenario - Design a URL Shortener (e.g., Bitly)Interviewer: "Design a scalable URL shortening service."1. Requirements & ScaleTraffic: $100$ million new URLs generated per month.Read/Write Ratio: It's a read-heavy system (e.g., 100 reads for every 1 write).Availability: Must be highly available. Redirection cannot fail.2. The Core LogicWe need to map a long URL (https://www.example.com/very-long-article-name) to a short alias (https://bit.ly/3xY8a).We can generate a unique 7-character string using base62 encoding (A-Z, a-z, 0-9). $62^7$ yields over $3.5$ trillion possible combinations.3. High-Level ArchitectureClient sends a request to shorten a URL.API Gateway/Load Balancer routes the request to an available Application Server.The Application Server generates the base62 short code.It checks the Database to ensure the code doesn't already exist (collision prevention).If unique, it saves the mapping (short_code : original_url) in a Relational Database (PostgreSQL) or a NoSQL store (MongoDB/DynamoDB).4. Resolving Bottlenecks (The "Senior" Touch)Bottleneck: Hitting the database for every single redirect will overwhelm it.Solution: Introduce a Redis Cache. When a user clicks a short link, the application first checks Redis. If the short code is in the cache (Cache Hit), it redirects instantly in $O(1)$ time. If not (Cache Miss), it queries the database, updates the cache, and then redirects.Bottleneck: The database is too large and write-heavy over time.Solution: Implement Database Sharding based on the first character of the short link.SummarySystem design is about managing compromises. There is no "perfect" architecture, only the right architecture for your specific traffic patterns, data strictness requirements, and budget. By mastering Load Balancing, Caching, and the CAP theorem, you demonstrate the architectural maturity expected of senior backend engineers.Additional ResourcesDesigning Data-Intensive Applications by Martin Kleppmann (The holy grail for backend engineers).System Design Interview by Alex Xu.
